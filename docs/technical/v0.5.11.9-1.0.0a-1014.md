## 技术变更

- 框架 4.1.13 → 4.1.14。上游 4.2.9 有三条会直接影响 AU 版的问题
  （`faceStyleSrcFn is not a function`、`whenSC2PassageEnd` 递归栈溢出、`UIBar is not defined`），
  实测在 4.1.14 上归零；升级面经字节级核对确认是纯钉版号替换。
  4.1.14 目前是唯一同时具备该导出、已验证补丁锚点并通过真机的 4.x 载荷。
- 作弊拓展 v1.20：上游 V1.20Beta 是可变通道（作者原位换包 5 次），本版钉住 2026-10-02 那一份，
  改走自建不可变镜像。
- 移除「变身兔兔」：与 0.5.11.9 + 4.1.14 组合下已无必要。
- **AU 变体目录优先级修正（契约层）**：AU 面部扩展在 9 处调用
  `faceStyleSrcFn(name, { variant: true })`，而 4.1.14 的该函数只声明一个参数，第二参数被丢弃。
  构建期在框架载荷里注入一条 needle 补丁，让双参数调用按 AU 原本的意图优先走变体目录。
  单参数调用逐字保持原行为；needle 不命中即构建失败。
  **这条补丁只修契约层，不改像素**：A/B 实测（桌宠画布全像素哈希）显示视觉结果与修补前逐像素相同。

## 未修复项：AU 面部扩展的「面纹 / 腮红 / 流泪」视觉未变

- 状态：`accepted_upstream` + `visual_incomplete`（**不是本版修复项**）。
- 2026-10-13 A/B 实测：变体目录 shim 改变了框架的解析路径，但桌宠像素与修补前完全相同。
- 两条独立原因：① 内置社区兼容层把扁平路径重映射到同一张 AU 真图；
  ② AU 的这三层在六个变体目录之间逐字节相同，只有眼睛等风格层因变体而异。
- 只有当新的 A/B 测到真实视觉改善时，状态才允许改成「已修复」。

## 未修复项：小人 / 桌宠眼球发白（2026-10-15 实测，方案 A 判定无效）

- 现象：侧栏角色精灵与桌宠小人的眼睛呈纯白、没有虹膜；同一画面的脸部特写正常。
- 影响的构建：0808（DoL 0.5.10.12 + 框架 4.1.13）正常；
  0915 与 1014（0.5.11.9 线）损坏，且 1014 与 0915 逐像素相同。
- 脸型范围：八个脸型里只有「碱性糖改脸」变化（眼带紫像素 20 → 0，白像素 87 → 119）。
- 已排除：框架版本（把 4.1.14 载荷换进 0808 仍正常）、AU 美术素材（两份包 sha 相同）、
  已加载贴图（`Renderer.ImageCaches` 哈希相同）、眨眼相位（连续 15 帧稳定）。
- 2026-10-15 新增证据（本轮）：0808 与 0915 的 `Renderer.ImageCaches` 状态**逐项相同**
  （同为 26 条缓存 / 9 条脸部条目），`Renderer.ImageErrors` 同为
  `eyes.png` / `mouth-smile.png` / `blush-1.png` 三条——也就是说 `eyes.png` 在**正常版**里同样缺失。
  两版之间唯一的请求级差异是 0915 多做一次 `img/face/碱性糖改脸/base-head.png` 失败探测。
- **方案 A（构建期补一张眼睛贴图）已用直接注入实验判定无效**。实验脚本在 `.local/eye-diag/`
  （`exp_eyes_control.py` / `exp_eyes_a1.py` / `find_registry.py`），方法是在 0915 产物里改写
  `Renderer.ImageCaches` 并强制重绘，再量测桌宠眼带（x88–122 / y26–50）紫/白像素：

  | 步骤 | 注入内容 | 结果（紫 / 白） |
  |---|---|---|
  | 基线 | 无 | 0 / 119 |
  | 阳性对照 | `sclera.png` 换成纯紫 | **338 / 6**（证明注入与重绘链路有效） |
  | 撤销对照 | 还原 | 0 / 119（可逆） |
  | A1 | `img/face/碱性糖改脸/base-head.png` = `img/body/base-head.png` 原件 | 0 / 119 |
  | A2 | `img/face/碱性糖改脸/Q萌一号/eyes.png` = 虹膜画布副本 | 0 / 119 |
  | A3 | A1 + A2 | 0 / 119 |

  结论：补齐这两个候选文件**不产生任何像素变化**，方案 A 判定 `no_visual_change`，
  按既定规则转入方案 B（修正合成顺序 / 缺图回退规则）。方案 B 需要单独设计，回归面更大，
  必须重跑 passage / scenario / combat / env 四套。

## 版本包与验收包的关系

tag 触发的 CI 会重新构建一次。构建输入（`lyra/`、`config/build.toml`、`config/mods.lock.json`）
与干跑时逐字节相同，但 ZIP / APK 内含打包时刻的文件时间戳，因此 sha256 不保证一致。
要核对手里的包，以 Release 页面上传的那份为准；上面那组摘要标识的是本轮真机验收所用的载体。
