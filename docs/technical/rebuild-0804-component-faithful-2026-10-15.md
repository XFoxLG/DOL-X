# 0804 整合包「组件忠实重建」记录（2026-10-15）

本文件记录 `v0.5.10.12-1.0.8a-0804` 的本地重建过程与对照验证结果。
目标不是「再构建一个 0804」，而是在原件只剩一件（AU-F APK）的前提下，
尽可能证明重建件与 2026-08-04 原件在**内容层面等价**，并把无法复现的部分
逐条列出。

相关路径：

- 原件对照物：`.local/release-assets-recovery/0804/DoL-0.5.10.12-XFox-1.0.8a-au-f-0804.apk`
  （sha256 `4370c73f…02f5c5c7`，132,345,566 B）
- 从对照物提取的输入件：`.local/release-assets-recovery/0804/embedded/`
- 本机重建驱动（不入库）：`.local/rebuild_0804_pipeline.py`
- 重建产物：`DOL-X-rebuild-0804\output\`（本机路径，与本仓库同级）

## 一、结果速览

| 项目 | 结论 |
|---|---|
| 重建 ZIP 四码字节数 | 与原件清单**完全一致** |
| 重建 APK 尺寸（正式密钥签名后） | 与原件清单**完全一致**（4/4） |
| 重建 AU-F APK vs 原件 AU-F APK | 21,939 个条目：**内容差异 0、头部差异 0** |
| `index.html` | **逐字节一致**（185,236,119 B、39 槽全等） |
| 签名块 `META-INF/DOL.RSA` | **逐字节一致**（用正式密钥签名后） |
| 剩余差异 | 仅 ZIP 条目**存放顺序**与**时间戳**（不影响任何内容） |

结论口径：**内容级完全一致，容器级仅剩顺序/时间戳**。
可以陈述为「与原件逐条目一致、含签名块」，但不等于「整个文件逐字节相同」。

## 二、两处实质差异及修复

首轮重建与原件对照后定位到两个会造成真实内容差异的问题，都已修复：

1. **槽 0（ModLoaderGui）取了错误的包**：原件内嵌 2026-01-20 构建
   （925,677 B），warmup 从上游 `latest` 拉到的是 2026-10-03 构建（+843 B）。
   修复：从原件 APK 提取该槽载荷，在下载步骤后覆盖缓存文件。
   （该载荷后来被 0713 原件独立验证为同字节，见 0713 档案。）
2. **槽 38（Lyra 元数据 mod）缺构建参数**：首轮未传 `--tag`，版本表写成
   `unknown` 且缺行。修复：按 tag 构建，并把生成的 Lyra zip 冻结为原件
   时间戳 `(2026, 8, 4, 13, 33, 28)` + `create_system=3`。

附带修复的构建环境差异：

- **换行符**：Windows 下 `Path.write_text` 会把 `\n` 写成 `\r\n`，与 Linux CI
  产物不同。驱动强制 `newline="\n"`。
- **进程模型**：上游用 `ProcessPoolExecutor`，子进程拿不到本机补丁；驱动改用
  `ThreadPoolExecutor`，让补丁在同一进程内生效。

版本表：`base/versions.json` 在 warmup 之后、build 之前用原件提取的 19 行
整体覆写，保证进入 HTML 的版本信息与原件一致。

## 三、签名密钥：本次最关键的发现

首轮重建用的是仓库根目录的 `dol.jks`（本地开发密钥，证书
`8C:6E:B4:D6:…`）。对照后发现：

- 原件 APK（0713 / 0804 / 0808 / 1014）全部由**同一把正式密钥**签名，
  证书 SHA-256 = `B2:1C:D1:5B:9F:F0:2D:60:3A:20:D9:4B:84:03:D5:D9:66:19:46:51:8F:88:E0:55:14:74:C9:3A:B8:29:EC:E6`
  （Subject `CN=DOL-X APK Signing Key, OU=Personal, O=XFoxLG, C=CN`）。
- 该正式密钥在本机有一份备份（放在仓库之外的私密目录，文件名带
  `DO_NOT_UPLOAD` 标记；别名 `dol`，PKCS12）。**密钥文件本身不得入库、
  不得上传、不得写进任何报告**；本文只记录证书指纹，指纹可以从任何
  一份原件 APK 用 `keytool` 独立复现。

用正式密钥重新签名后：

- 4 个 APK 的字节大小与原件清单**逐一完全一致**
  （base 81,829,040 / au-f 132,345,566 / au-m 124,497,630 / au-a 130,449,118）。
- `META-INF/DOL.RSA`（含签名块）、`DOL.SF`、`MANIFEST.MF` 与原件**逐字节相同**。
- 逐条目比较：21,939 条**内容全部相同**，压缩方式 / 压缩后大小 / 标志位 /
  ZIP 版本字段 / extra 字段**全部相同**。

这条发现同时意味着：用正式密钥签名的重建版可以**覆盖安装**在玩家现有的
同包名安装之上；用开发密钥签名的版本不行（Android 会拒绝更新安装）。

## 五、与原件差异的完整分类

**内容差异：0。**

**容器差异**

- ZIP 条目**存放顺序**不同（原件的写入顺序与本地 Python 写入顺序不同）。
- ZIP 条目的**时间戳**不同（原件是 CI 构建时刻，本地是本次构建时刻）。
  做过实验：把 21,939 个条目的时间戳逐个改成原件值后，文件哈希仍不同，
  证明顺序差异确实存在且独立于时间戳。

这两项不影响解包内容、不影响安装、不影响运行。

**载体结构性差异**（ZIP 与 APK 两种载体的固有区别，不是构建错误）

- 重建 ZIP 比 ZIP 原件多 3 个文件（`CREDITS.md` / `LICENSE` / `README.md`）；
  APK 多 7 个 Cordova 脚手架文件。

## 六、验证方法

- `verify_apk_equivalence.py`：按文件名逐条目比较**未压缩数据的 sha256**
  以及压缩方式 / 压缩后大小 / 标志位 / 版本字段 / extra 字段。
- `compare_slots.py`：解析 `window.modDataValueZipList`（分隔符是 `", "`，
  不是 `","`）逐槽比较。
- `index.html` 全字节比较（185,236,119 B，0 个 CRLF）。
- `keytool -printcert -jarfile` 比较签名证书指纹。

## 七、边界

- 0804 **AU-F APK** 有原件，因此能做到「逐条目一致（含签名块）」；
  其余 7 件原件已丢失，只能做**尺寸级 + 组件级**验证。
- 重建件与原件**不是同一个文件**（顺序/时间戳不同），不得写成
  「与原件逐字节相同」；可以写「逐条目内容一致，含签名块」。
